# Investigate Failed Requests and Complete Incident Review

ParcelTrack operators cannot follow failed delivery updates because structured log output uses incorrect field names. Incident draft mixes event order and blames an individual without identifying missing system safeguards. Restore searchable logs and produce evidence-based incident findings.

Module 5 only (LU 5.3, 5.5). Local, free, no cloud account or credentials.

## Before 30-minute timer

Fork https://github.com/kalviumcommunity/request-incident-review and clone your fork. Python 3.9+ standard library, terminal, editor and PDF/screenshot tool must already work. No package install. Run commands from repository root. Report unrelated environment failures to instructor and pause timer. Q3 binds ephemeral localhost ports and terminates only processes it creates. Windows may use `python` instead of `python3`.

## Application/evidence contract

Each event already has one timestamp, severity, request ID generated once per request, and message. formatter.py must emit exactly timestamp, level, request_id, message, preserving every value and one JSON object per line. Correct four keys; do not change request context or fixture data.

The trace command filters request_id=r17 and prints the recorded incident lifecycle. This is provided, sanitized historical evidence, not a live outage generated by the student. Timeline entries must cite the UTC timestamps from these events.

fixtures/change-record.md documents a mistyped storage endpoint, syntax-only checks, release without staging connectivity validation, rollback and verified recovery. Use only these facts. Five-line postmortem: three causal statements leading from symptom to systemic missing guardrail, then two specific prevention actions with a named owner and explicit due date. Five whys is a method, not a requirement for exactly five questions. Any evidence-supported equivalent wording is accepted.

## Exactly three task groups

1. Restore structured records — 4 code lines — 6 marks. Replace four incorrect JSON keys with documented core fields; retain supplied values. Show actual emitted JSON records and checker result.

2. Reconstruct incident — 4 written lines — 7 marks. Filter failed request with supplied command. Replace four timeline lines: detection, triage with impact/roles, mitigation and verified recovery. Preserve UTC chronology and distinguish received request from detection alert.

3. Replace blame with prevention — 5 written lines — 7 marks. Read supplied change record. Replace five draft lines with three linked evidence-supported causal statements ending at missing system guardrail, plus two concrete actions with named owners and due dates. No invented monitoring or deployment results.

## Commands (complete in order)

```bash
python3 check.py records
python3 check.py trace
python3 check.py review
```

Permitted edits: **formatter.py (four JSON keys only), timeline.md, postmortem.md**. Do not change check.py, support.py, drill.py, fixtures, generated evidence or targets. Tasks are independently callable; Task 1 repair is needed for Q2 trace, but written analysis may be drafted from supplied evidence. Report commands may run successfully even when written drafts are wrong: a PASS line validates only runtime/configuration, NEVER correctness of prose. Written answers are manually graded against evidence, not exact keywords.

Each task is one fault/incomplete-analysis group, not necessarily one bad line. Three-to-five meaningful content lines per task; existing scaffolding supplied. Braces/blank lines/comments and editor wrapping do not count. No artificial line padding. Normal JSON pretty-printing may expand formatting without increasing task scope.

## Submission

One PDF, three labelled task sections, fork URL as text, readable real command output and corrected diff/file, requested 3–5-line analysis (PDF text or editor screenshot). Show failing configuration output before repair and passing output after for code/config tasks; written tasks show supplied source evidence and corrected analysis. Minimum one real screenshot per task; combine related evidence if readable or use extra screenshots. No PR/video/ZIP required. Commit corrections to your own fork; evaluator grades PDF, not private account access. Suggested 5 minutes diagnosis, 18 minutes repair/analysis, 7 minutes verification/PDF. Never fabricate results or include secrets. Checker success does not replace written reasoning or screenshot proof.

Protected sources are starter implementation of previously taught operations concepts, not new Python algorithms students must implement. Do not distribute instructor reference solutions with this repo.
